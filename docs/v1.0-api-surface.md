# v1.0 Public API Surface Audit

> **SSOT**: This document is the single source of truth for the public API
> surface that will be frozen at v1.0. After v1.0 release, every header listed
> in [Public API Surface](#public-api-surface) is governed by SemVer and may
> not be removed, renamed, or have its public symbols altered without a major
> version bump.

> **Scope**: All headers under `include/kcenon/network/` excluding the
> `detail/` subtree. Detail headers are implementation-detail and remain
> outside the v1.0 contract.

> **Audit horizon**: This audit was conducted against
> [`develop`](https://github.com/kcenon/network_system/tree/develop)
> as of 2026-05-10 and produced as part of
> [#1125](https://github.com/kcenon/network_system/issues/1125)
> (Part of [#964](https://github.com/kcenon/network_system/issues/964)).

## Audit Method

1. Enumerated every file under `include/` matching `*.h` or `*.hpp`. Excluded
   the `detail/` subtree because those headers are documented as
   implementation-detail (see `include/kcenon/network/utils.h` and the
   per-umbrella header notes in `unified.h`, `config.h`, `concepts.h`).
2. Catalogued top-level namespaces, classes, structs, enums, free functions,
   templates, and using-declarations from each public header.
3. Scanned all public headers for `[[deprecated]]`, `_DEPRECATED`, and
   "deprecated" prose. The CI job `.github/workflows/public-api-check.yml`
   independently enforces "no `throw` in public headers"; this audit does
   not duplicate that gate.
4. Cross-checked against the downstream Tier 5 consumer
   ([`pacs_system`](https://github.com/kcenon/pacs_system))
   to identify which public headers are actually used in production.
5. Classified each header into one of four buckets:

   | Bucket | Meaning |
   |--------|---------|
   | `stable` | Frozen at v1.0. No breaking changes for the v1.x line. |
   | `rename-candidate` | Naming inconsistency that should be addressed before freeze. |
   | `remove-candidate` | Deprecated or unused; should be removed before freeze. |
   | `experimental` | Out of scope for v1.0; stays under `detail/experimental/` or behind a feature flag. |

6. The `experimental/` directory under `include/` was already migrated to
   `src/internal/experimental/` per
   [#577](https://github.com/kcenon/network_system/issues/577); no
   experimental headers remain on the public surface.

## Per-Header Classification

### Group: Umbrella

Convenience aggregators that re-export functionality from other groups.
Downstream consumers typically include exactly one umbrella header.

| Header | Top-level symbols | Classification | Rationale |
|--------|-------------------|----------------|-----------|
| `network_system.h` | `kcenon::network::initialize()` (3 overloads), `shutdown()`, `is_initialized()` | `stable` | Single entry point for typical usage. The 3 `initialize` overloads cover defaults / standalone-with-config / external-dependencies and are documented in the header. |
| `forward.h` | Forward declarations across `core`, `session`, `protocol`, `internal`, `http`, `security` namespaces | `stable` | Pure forward-declaration header. Adding new forward declarations is non-breaking; removing one would break downstream code that relies on it. |
| `utils.h` | Re-exports `types/result.h` and detail lifecycle/callback helpers | `stable` | The detail headers it pulls in are part of the public surface contract because they appear in the public umbrella chain. |

### Group: Concepts

| Header | Top-level symbols | Classification | Rationale |
|--------|-------------------|----------------|-----------|
| `concepts/concepts.h` | `kcenon::network::concepts` namespace; `using` re-exports of `kcenon::common::concepts::{Resultable,Unwrappable,Mappable}` when `KCENON_WITH_COMMON_SYSTEM` is defined | `stable` | Concept names are part of the API; renaming would break SFINAE / `requires` clauses in user code. |

### Group: Configuration

| Header | Top-level symbols | Classification | Rationale |
|--------|-------------------|----------------|-----------|
| `config/config.h` | Re-exports `feature_flags.h`, `network_config`, `network_system_config` (the latter two from `detail/config/`) | `stable` | Documented umbrella; downstream code is expected to include this rather than the detail headers. |
| `config/feature_flags.h` | `KCENON_WITH_COMMON_SYSTEM`, `KCENON_WITH_THREAD_SYSTEM`, `KCENON_WITH_LOGGER_SYSTEM`, `KCENON_WITH_CONTAINER_SYSTEM`, `KCENON_WITH_MONITORING_SYSTEM` macros | `stable` | Macros gate optional integrations; renaming would break user build configurations. |

| Header | Top-level symbols | Classification | Rationale |

| Header | Top-level symbols | Classification | Rationale |

## Deprecation Audit

A `grep -rn 'deprecated\|_DEPRECATED'` across `include/` returned **zero
matches outside the `detail/` subtree**. Specifically:

- `include/kcenon/network/detail/utils/result_types.h:44` and `:54` —
  internal type aliases marked "deprecated for external use". These are
  not on the v1.0 public surface (they live under `detail/`) and the
  `Result<T>` umbrella in `types/result.h` already steers users to the
  public path.
- `core/README.md` mentions "All non-deprecated APIs in this module are
  stable" — prose only, no symbols.

**No `[[deprecated]]` symbols are present on the public surface.** No
removal action is required prior to freeze.

> Runtime deprecation note: `policy::no_tls` ships a runtime warning
> recommending TLS-enabled policies in production
> (see [#871](https://github.com/kcenon/network_system/issues/871)). The
> warning is operational guidance — the type itself remains supported and
> is not marked `[[deprecated]]` because plain-text transport remains a
> valid development and intra-trust-boundary use case.

## Freeze Recommendations

### Naming Inconsistency Note

The integration headers
(`integration/network_system_bridge.h`,
`integration/thread_integration.h`)
mix camelCase (`NetworkSystemBridge`, `NetworkSystemBridgeConfig`) and
snake_case (`thread_pool_interface`, `thread_integration_manager`)
within the same namespace. This is a **known stylistic artifact** of the
integration-bridge era (#579 et al.).

**Recommendation: do not rename.** The camelCase types are public,
referenced from a number of downstream applications, and the rename
churn cost outweighs the stylistic benefit. The public-API freeze
locks both styles in place; future code should follow snake_case but
existing camelCase types are part of the contract.

### Rename Discussion

The audit considered these rename candidates and rejected each:

| Candidate | Rejection Reason |
|-----------|------------------|
| `NetworkSystemBridge` -> `network_system_bridge` | High downstream churn; documented camelCase API would be broken. |
| `network_system::integration` legacy alias removal | Used by historical downstream code paths; alias is one line, cost-of-keep is zero. |
| `i_*` interface prefix simplification | Prefix is well-established and self-documenting; no rename benefit. |
| `Result<T>` -> `result<T>` | Aligns with `kcenon::common::Result<T>` upstream; renaming downstream would create asymmetry. |

### Final Freeze List

- All 31 public headers ship as-is at v1.0.
- The `detail/` subtree (34 headers) remains free to evolve in v1.x patches.
- The `experimental/` directory contains no headers and is preserved as
  a placeholder for future experiments under the
  `internal::experimental::` migration path documented in
  `include/kcenon/network/experimental/README.md`.

## Maintenance After Freeze

Once v1.0 is tagged, the following invariants apply to every header in
[Public API Surface](#public-api-surface):

1. **No symbol removal.** A symbol that exists on the public surface at
   v1.0 may not be removed for the entire v1.x cycle. Use `[[deprecated]]`
   to signal intent; remove only at v2.0.
2. **No rename.** Renaming a public symbol is a breaking change.
3. **No signature change.** Argument types, return types, parameter
   names exposed in headers, default arguments, exception specifications,
   `noexcept` qualifiers, template parameter packs, and concept
   constraints are all part of the contract.
4. **No `throw` introduction.** Enforced by
   `.github/workflows/public-api-check.yml`. Public functions either
   return `Result<T>` / `VoidResult` or are `noexcept`.
5. **Adding new symbols is non-breaking** as long as it does not shadow
   or conflict with existing usage.
6. **Adding new overloads is non-breaking** as long as it does not change
   overload resolution for existing call sites in observed downstream
   code.

### CI Enforcement

Existing CI gates that protect the surface:

- `.github/workflows/public-api-check.yml` - "No `throw` in public headers"
- `.github/workflows/public-api-check.yml` runs on every PR targeting
  `main` or `develop`.

After v1.0 release, consider adding:

- A header-symbol diff job that fails if a public header in this audit
  removes or renames a top-level symbol. (Tracked as future work; not
  blocking the freeze.)

### Process

1. Tag v1.0.0 from `main` after the v0.x to v1.0 release PR merges.
2. Update `CHANGELOG.md` (root) and `docs/CHANGELOG.md` with the
   "API freeze for v1.0" entry pointing at this audit.
3. Update `CONTRIBUTING.md` with the v1.0 freeze policy (this is done
   in the same PR as this audit).
4. Open a follow-up issue under
   [#964](https://github.com/kcenon/network_system/issues/964) for any
   v1.x-deferred items identified during the freeze window.
